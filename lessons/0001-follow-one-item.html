一顆蘋果如何穿過整個系統

目標：面試時，能解釋「按下移動後，資料怎麼存下來，畫面為什麼會變」。先只理解這一條路徑。

情境：待購有三顆蘋果，使用者移動一顆到庫存。前端傳送物品 ID、數量 1、目標狀態 IN_PANTRY。

六個步驟

  1. 卡片通知上層。PantryItemCard 呼叫 props 傳入的 onMove(item.id, 1, 'IN_PANTRY')。它不直接操作資料庫。
  2. 頁面協調操作。KanbanBoard 將 callback 傳給卡片；callback 實際指向 DashboardPage.handleMove，再呼叫 usePantry 提供的 mutation。
  3. Apollo 發出請求。usePantry 封裝 GraphQL 文件和 Hook；Apollo 的 auth link 附上 token，送到 /api/graphql。這一步跨越瀏覽器與伺服器。
  4. Next.js 接住 HTTP 請求。app/api/graphql/route.ts 匯出 HTTP handler，透過 adapter 交給 Apollo Server。context 處理 token，提供 userId；GraphQL schema 定義操作及輸入型別。
  5. Resolver 執行业務邏輯。moveItem 檢查使用者及物品歸屬。部分移動時，透過 Prisma transaction 扣除來源數量，並建立或合併目標資料。持久化位置是 PostgreSQL。
  6. 重新取得資料，再渲染。moveItem 設有 refetchQueries，操作成功後重新查詢。Apollo 提供更新的資料給 React，看板依 boardState 分組，顯示待購兩顆、庫存一顆。

第六步是這個專案 moveItem 的策略。Apollo 也能直接更新 cache；並非每個 mutation 都必須 refetch。參考 Apollo 官方說明。

你用了哪些 React 能力？

Component 拆開頁面、看板和卡片；props 傳資料及 callback；custom Hook 封裝資料操作。搜尋字串、dialog 開關等 UI 狀態由 useState 管理；資料庫資料則經由 Apollo query/cache 取得。

勾選食材是另一個例子：selectedItemIds 放在共同父元件 DashboardPage，讓看板顯示勾選，也讓 AIRecipeManager 取得食材 ID。這符合 React 的狀態提升原則。

你用了哪些 Next.js 能力？

app/page.tsx 對應首頁，layout.tsx 組合共用外框與 providers；Route Handler 承載 GraphQL API。首頁標記 'use client' 來支援互動，庫存主要由 client 端 Apollo 取得，沒有在首頁 Server Component 中預先讀取 Prisma。

Client Component 仍可能參與初次 HTML 預先渲染；不要把 use client 解釋成「所有程式都只在瀏覽器執行」。參考 Next.js 官方說明。

合上上面的說明，再練習

只勾選一顆蘋果，會不會寫入資料庫？先說出理由。

這條操作不會。toggleSelection 更新頁面中的 Set 狀態，React 重新渲染勾選與 AI 按鈕；沒有發起 mutation。移動、刪除、儲存才有各自的資料操作。

usePantry 是後端嗎？請說出真正跨越網路的位置。

不是。usePantry 是 Client Component 使用的 Hook。Apollo 將 GraphQL operation 送到 /api/graphql 時，才跨越網路進入伺服器處理。

為什麼移動後要重新查詢？先想一個部分移動的例子。

一次移動可能同時影響來源與目標，甚至新增或刪除資料。重新查詢可簡化前端同步邏輯，代價是額外請求；目前查詢還會一併取得食譜。

面試口述練習

我把看板拆成頁面、看板與卡片。卡片透過 callback 回報操作，頁面使用 usePantry 封裝的 Apollo mutation。Next.js 的 Route Handler 承載 GraphQL，resolver 驗證物品歸屬，再透過 Prisma 寫入 PostgreSQL。移動可能拆分或合併資料，所以目前成功後重新查詢，讓 React 根據最新資料更新看板。
